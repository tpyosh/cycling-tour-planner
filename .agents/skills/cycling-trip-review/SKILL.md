# サイクリング旅行の批判的レビュー

現行案を初めて見る案と同じ基準で監査し、弱い時間帯や破綻条件を具体的に示す。レビューの目的は現行案の擁護ではなく、旅行者が安全に判断できる材料をそろえることである。

## 開始条件

`trip.yaml`、`constraints.yaml`、`plan/current.yaml` と、参照される候補、根拠、距離、宿泊調査、Issueを読む。

- 時刻、接続、日没、宿泊、規制、参照整合性を監査するときは [references/feasibility-and-data.md](references/feasibility-and-data.md) を読む。
- 現地体験、自走する意味、日ごとの密度、旅全体の線、現行案の再評価を監査するときは [references/experience-and-structure.md](references/experience-and-structure.md) を読む。
- 全体レビューでは両方を読む。

## ワークフロー

1. 固定制約と評価軸を明示し、作成経緯や既投入工数から独立して見る。
2. 各日を時間順にたどり、成立条件、余裕、撤退手段、翌朝への接続を確認する。
3. 各候補と自走区間について、旅行者の具体的な行動、視界、体験時間、反復、自走する利得を確認する。
4. 旅行全体の体験密度、移動効率、線の自然さ、朝夕、交通障害への耐性を別軸で比較する。
5. 指摘を重大度順に並べ、維持、一部降格、大幅降格、削除、代替のいずれかを提案する。変更で改善する軸と失うものを併記する。
6. 根拠不足は未確認として残し、必要なら `$cycling-trip-research` へ調査論点を渡す。

独立した監査観点を主スレッドから分離する価値がある場合は、読み取り専用の `trip_critic` に委任してよい。成立性と体験価値を並列化する場合も、親エージェントが指摘を統合してから一度だけ編集する。

## 終了条件

- 重大な指摘に、対象ファイルまたは安定ID、根拠、影響、改善案がある。
- 維持する箇所にも、具体的な体験価値または成立根拠がある。
- 未確認事項を解決済みとして扱っていない。
- 変更を加えた場合、`tools/validate.py`、`tools/render.py`、関連テストが成功する。
