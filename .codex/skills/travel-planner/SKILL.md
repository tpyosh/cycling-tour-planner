# Travel Planner

旅行者が現地で判断できる計画を作る。名所の羅列ではなく、固定条件を守り、移動と滞在がつながり、変更時の影響を追える状態を成果とする。

## 最初に把握すること

分かっている範囲で次を整理する。不足があっても、安全性や予約可否を左右しない限り、合理的な仮定を明示して先へ進む。

- 日付、人数、出発地、帰着期限
- 予約済み・変更困難な交通や宿
- 利用できる交通手段と、荷物・自転車・車両などの制約
- 体力、経験、許容する一日当たりの移動量
- 必須体験、避けたいこと、旅の評価軸
- 予算、宿の条件、食事条件
- 天候、季節、日没、潮汐、通行規制などの安全条件

ハード制約と好みを分ける。ハード制約を満たせない案は推薦せず、成立させるための変更点を示す。

## 計画の組み立て方

1. 予約済み交通、帰着期限、特定日時の時間窓を固定アンカーとして置く。
2. 地域、道路、体験、食事、交通の候補を広く発見する。この段階では、珍しさや発見時の印象で順位を決めない。
3. 候補ごとに、一般旅行者が現地で行うこと、見えるもの、アクセス、必要時間を確かめる。説明できない候補は調査中のままにする。
4. 体験の強さ、旅全体での役割、似た体験との反復、自転車を使う利得を評価し、固定滞在、通過観察、保留のいずれで扱うか決める。
5. 採否に関わる営業時間、運行、通行規制、持込条件を確認する。成立性が不明な候補で日割りの空欄を埋めない。
6. 昇格条件を満たした候補を旅行全体の流れとして組み、各日の主役、終着地、翌朝の開始位置を決める。
7. アンカー間を移動区間でつなぎ、自転車と公共交通の役割を決める。所要時間だけでなく、体験価値と乗換・積み降ろしを含む負担を比較する。
8. 行き先の大枠が固まってから、時刻、食事、補給、入浴、荷物、チェックイン締切など運用の詳細を確認する。
9. 破綻しやすい接続ごとに、削る順序・代替交通・代替宿泊地を用意する。

所要時間の平均値だけで成立させない。乗換、受付、積み降ろし、道迷い、休憩、撮影、混雑、天候悪化を別に見積もり、重要な締切の前に余裕を置く。

## 候補を旅程へ昇格させる

発見と順位付けを別工程にする。希少性、知名度、歴史的重要性、写真映え、公式説明の強さは候補を発見する手掛かりであり、旅行者の体験価値そのものではない。

強い候補、一日の主役、主要ルートとして推薦する前に、次の Actionability Gate を満たす。

- 到着後の行動、観察地点または移動範囲、実際に見えるものを具体化できる
- 一般旅行者が通常の条件で合法かつ安全に実行できる
- 移動を除く現実的な体験時間と、旅全体での役割を概算できる
- 自転車区間なら、自転車によって増える体験を説明できる
- 根拠が通常の旅行者の条件と整合し、特別公開や撮影条件を混同していない

満たさない候補は、未確認点を `unverified` として記録し、調査状態を `researching` に留め、主要旅程へ入れない。通過中の観察で価値を得られる対象は、専用の滞在時間を設けず `pass_through` として扱う。評価方法の詳細が必要なら [references/experience-evaluation.md](references/experience-evaluation.md) を読む。

## 旅程全体の構造を比較する

旅行全体を一本の線として評価する。朝の開始位置から最初の体験へのつながり、一日の景観・産業・地形の変化、前日の終点と翌日の主役との接続、逆走や同一路線往復の量、交通手段を替えたときの地理的な連続性を見る。線の自然さは評価軸の一つとし、弱い半日や大きな待ち時間との交換条件を明示する。

宿泊地は翌朝の開始位置としても評価する。朝の時間帯に価値が集中する体験があるなら、前夜に近くまで進む便益を見込む。午後の早い到着後に有力な行動がない場合は、前の強い場所へ時間を配分し、制約を満たす範囲で夕方に宿泊地へ入る案も比較する。

輪行などの公共交通は、駅までの移動、準備、待ち、乗車、乗換、解除、時刻表拘束を含む総負担で評価する。短縮時間ではなく、価値の低い長距離区間をまとめて置換する、体験価値の低い時間帯へ移動を寄せる、翌朝を強い体験の近くで始める、半日以上を強い区間へ渡す、営業時間や交通制約を解消するといった旅程構造の改善を重視する。目標は、不自然な輪行と価値の低い自走の両方を減らすことに置く。

案を比べるときは、体験密度、移動効率、線の自然さ、自転車を使う意味、朝夕の使い方、交通障害への耐性を別々に示す。日数は固定の充填枠とみなさず、弱い半日しか残らないなら、短縮、地域の差替え、公共交通による移動、帰着への充当も比較する。総合順位を付ける場合も、軸ごとの優劣と交換条件を残す。

## 現行案を再評価する

再監査では、現行案を初めて見る案と同じ基準で評価する。評価根拠には各区間と時間帯から現在得られる実質的な価値を用い、調査や設計に費やした時間から独立させる。弱い時間帯はそのまま示し、休息、余白、移動日、学習による価値を後付けの採用理由にしない。必要な休息や余白には、必要性と得られる効果を説明する。

ユーザーから疑問が出た場合は、問いを再監査の契機として扱い、当初の評価根拠と現地行動へ戻って同じ評価軸で確認する。問いの方向へ反射的に結論を変えない。維持、一部降格、大幅降格、削除のいずれかを独立して判断し、維持する案には具体的な価値を、変更する案には改善する軸と失うものを示す。

## 情報の扱い

調査結果は `fact`、`inference`、`unverified` を区別し、「主張」「出典」「確認日」「変動性」「再確認要否」の組で保持する。複数の事実から導いた判断を事実として記録せず、未確認事項を推測で埋めない。時刻、運賃、営業、予約在庫、道路・航路の運用は変わる前提で扱い、利用者の旅行日に有効な公式情報を優先する。

不明を推測で埋めない。特に次を区別する。

- 情報が見つからない
- Web予約枠がない
- 指定条件ではWeb予約できない
- 電話確認が必要
- 満室・運休・休業が明示されている

予約、購入、電話、メッセージ送信など外部状態を変える操作は、旅行者の明示的な依頼なしに行わない。

詳しい調査方法と鮮度管理が必要なら [references/research-and-risk.md](references/research-and-risk.md) を読む。

## 計画データの分離

複雑な旅行では、次を別々に管理する。

- `constraints`: ハード制約とソフト制約
- `catalog`: 候補地、経路、交通、宿泊地域、食事
- `plan`: 現在採用している日別計画
- `evidence`: 調査済みの事実と出典
- `issues`: 未確認事項、影響、次の確認、解決条件
- `estimates`: 距離や時間の計算結果と計算方法
- `research`: 宿など、候補比較や確認作業が多い領域
- `docs`: 旅行者が読む旅程、ピン一覧、確認リストなどの生成物

候補の状態と現行計画への採用を同じフィールドで表さない。候補は `discovered`、`researching`、`shortlisted`、`deferred`、`rejected` などで管理し、採用は `plan` からの参照で表す。

構造化された旅行ワークスペースを作る場合は、[references/data-model.md](references/data-model.md) を読み、`assets/starter/` の雛形を必要な範囲だけコピーして具体化する。小規模な旅行ではこの構造を無理に導入しない。

## 実現可能性の確認

各日について、最低限次を確認する。

- 出発可能時刻と到着締切
- 区間ごとの所要時間、距離、標高、路面、交通量
- 公共交通の接続、受付締切、持込み条件
- 営業時間ではなく、最終入場・潮汐・天候など実際の利用可能時間
- 宿泊地の候補数、食事・補給、最終チェックイン
- 日没後に残る距離と、撤退・短縮手段

時間窓がある場所は、窓の端への到着を計画しない。公式の時間窓を基準に余裕を置き、天候などで利用不能になる条件を当日判断として残す。

自転車・徒歩などの累計距離は、鉄道、フェリー、航空、車への切替地点で区間を分ける。表示値、元データ、計算方法を分離し、再計算しても旅程本文を直接書き換えない設計を優先する。

## 代替案と未解決事項

通常旅程と、発動条件付きの代替案を混ぜない。代替案には、発動条件、固定するもの、失われる体験、圧縮する区間、未決事項を記録する。

現行計画を左右する不確実性は issue として管理し、少なくとも次を含める。

- 要約
- 放置した場合の影響
- 関連日・関連対象
- 根拠
- 次の確認行動
- 解決とみなす条件

単なる調査メモは issue にしない。時間、安全、予約、接続、計画選択に影響するものだけを残す。

## 成果物

最終旅程は旅行者向けの運用スナップショットにする。調査過程や出典一覧を転載せず、各日に必要な移動、確定事項、任意項目、重要な注意、未解決リスクへの参照を載せる。

明確に区別して書く。

- 確定済み・予約済み
- 推奨するが未予約
- 任意
- 未確認
- 直前または当日判断

提示前に [references/quality-check.md](references/quality-check.md) のチェックを行う。大きな変更後は、参照切れ、日付順、重複、移動の連続性、制約違反、閉じた issue の記録を検査する。
