# 旅行計画のデータモデル

この資料は、数日以上の周遊、複合交通、多数の候補、再調査が必要な旅行をファイルで管理するときに使う。

## 推奨構成

```text
trip.yaml
constraints.yaml
catalog/
  places.yaml
  routes.yaml
  stay-areas.yaml
  transport.yaml
  food.yaml
plan/
  current.yaml
evidence/
  sources.yaml
estimates/
  distances.yaml
research/
  lodging.yaml
issues.yaml
docs/
  itinerary.md
  pins.md
  issues.md
```

YAMLを正本とし、旅行者向けMarkdownは生成物として扱う。履歴は同じファイルの複製ではなくGitで残す。予約開始時、主要予約完了時、出発直前など、意味のある時点だけタグや明示的なスナップショットを使う。

## IDと参照

対象には安定したIDを付ける。表示名を変えても参照が壊れないようにする。

- `place.*`: 立ち寄り先、起終点
- `route.*`: 移動経路
- `stay.*`: 宿泊地域
- `transport.*`: 列車、便、フェリーなど
- `food.*`: 飲食・補給
- `evidence.*`: 根拠
- `issue.*`: 未解決事項

現行旅程は対象を複製せず、IDで参照する。候補の採用状態を `adopted` のようなフラグで重複管理しない。

## 候補の発見と評価

候補を見つけた記録と、旅程へ採用する評価を分ける。発見時は対象、場所、情報源、特徴を記録し、順位付けは旅行者の具体的な行動、想定時間、旅全体での役割、移動や待ち時間の増減を確認してから行う。

候補の調査状態は、`discovered`、`researching`、`shortlisted`、`deferred`、`rejected` などで管理する。現行計画への採用は候補側へ重複して記録せず、`plan` からの参照で表す。

計画から参照する候補には、必要に応じて次の `visit_mode` を付ける。

- `dedicated_stop`: 専用の滞在時間を設ける
- `pass_through`: ルート上で自然に観察し、専用の滞在時間を設けない

評価を構造化する場合は、単一スコアだけでなく、体験の強さ、移動効率、旅程の連続性、自転車を使う意味、朝夕への効果、交通障害への耐性を保持する。`pass_through` には、どの区間で何を観察できるかを記録する。

## 距離・所要時間

次の3層を分ける。

1. データ: 起点、対象、累計値、確信度、計算日、参照先
2. 計算: ルーティングAPI、地図、公式距離、手計算など
3. 表示: 採用済みの値だけを旅程に表示

比較用の再計算を保存する場合は、表示対象を一つに限定する。徒歩・自転車から公共交通へ切り替えたら、新しい segment として累計を再開する。

## 宿泊調査

宿泊地域を先に計画へ置き、宿候補は別の調査台帳で管理する。候補ごとに、対象日、人数、部屋数、食事条件、立地適合、Web判定、電話要否、確認結果、出典を残す。

電話確認前は空室や料金を `unknown` のままにする。確認待ちの候補に、推定の結果を入れない。電話では「駐輪場の有無」だけでなく、客室持込み、管理された屋内保管、施錠、輪行袋の要否、事前連絡の順で確認する。

## 雛形の使い方

`assets/starter/` は概念をすぐ使い始めるための最小雛形であり、完全なスキーマではない。旅行の複雑さに応じて不要なファイルやフィールドを省く。逆に、予約情報や安全判断を機械的に検証したい場合はJSON Schemaと検証スクリプトを追加する。
